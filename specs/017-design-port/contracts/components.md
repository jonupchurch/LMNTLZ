# Phase 1 — Contract: The Component Layer

**Date**: 2026-07-30 · **Plan**: [plan.md](../plan.md)

The public surface of `apps/client/src/components/`. This is the interface 014, 015,
016 and every screen in 018 will build against, so it is a contract rather than an
implementation note.

---

## The three rules that shape every signature

**1 · A component never accepts a colour.** It accepts the *thing*, and derives.

```ts
<TypeBadge type="fire" />          // ✅ colour derives from the force
<TypeBadge color="#E8552B" />      // ❌ colour becomes a second source of truth
```

Constitution XV. A colour prop lets a caller paint Fire with the Water token and
nothing catches it. Applies to `TypeBadge`, `RelationshipStrip`, `HeroCard`,
`EffectivenessGrid`, `Meter` and every force-tinted surface.

**2 · A multiplier is `Effectiveness`, never `number`.**

```ts
import type { Effectiveness } from '@lmntlz/content';   // 1.5 | 1.25 | 1.0 | 0.8 | 0.5
```

Four exports print `FAULT ×1.2` and none prints `×0.80`. Typing on the union makes
the design's wrong ladder **unrepresentable** — the compiler enforces FR-019 at no
cost. Same rule for any cap or threshold: read it from the generated source.

**3 · A duration is turns.** `CooldownRing` takes `turnsRemaining` and
`turnsTotal` — never milliseconds, never a `Date`. Constitution XIII; combat is
discrete and a ring that animates against a clock is a rules claim made in CSS.

## Shell

```ts
AppShell({ rail, header, children })
Rail({ entries, activeId })
RailEntry  = { id, label, badge?, children? }   // `children` groups THE COURT
Header({ shards, username, connection, onProfile })
```

**`RailEntry` has no `href` for a destination that does not exist** (FR-015). The
rail is built from the destinations the app actually registers, so an unbuilt screen
cannot appear. 017 registers Squads · Roster · Matchmaking · The Court · Codex; 018
adds Rune Forge and The Store; 016 adds Dispatches.

`AppShell` reserves the Electron title-bar/drag region as a **slot it does not
fill** — there is no Electron at 1.0, and building the frame now would be an unused
implementation rather than an unused seam.

## Controls

```ts
Button({ variant, state?, size?, onClick, children })
// variant: primary | secondary | ghost | danger
// the SEVEN states from the export are covered by variant × { rest, hover,
// active, focus, disabled, loading, success } — all seven rendered in the gallery
```

Never `outline: none`. `:focus-visible` is set globally in `base.css` and a
component may not override it.

## Type & relationships

```ts
TypeBadge({ type, size? })                       // type: DamageType
RelationshipStrip({ hero })                      // renders FIVE tiers
EffectivenessGrid({ attacker?, defender? })      // the 9×9 heat readout
```

`RelationshipStrip` shows Bane ×1.50 · Fault ×1.25 · neutral ×1.00 · secondary
×0.80 · primary ×0.50, **all five read from `@lmntlz/content`**. This is the one
place the port deliberately departs from the design, and the departure is recorded
in `resources/README.md`.

## Hero

```ts
HeroCard({ hero, scale, runes?, onSelect? })     // scale: 'compact'|'standard'|'full'
PowerSlot({ power, turnsRemaining, gated })
CooldownRing({ turnsRemaining, turnsTotal })
HeroIcon({ heroId, size? })                      // heroId is typed; a typo is a build error
```

All three scales carry the same data; only density differs, so a caller never
loses information by choosing a smaller one.

## Readouts & system

```ts
Meter({ value, max, tone? })
Pill({ children, tone? })
StatusPip({ kind, stacks?, sealed? })            // ⚠️ see below
ConnectionState({ status, latencyMs? })
```

> **`StatusPip` ships with no producer.** Nothing in the codebase constructs a
> `StatusInstance`; `board.ts` hardcodes `statuses: []`. The component and its
> 71-icon registry exist because the design specifies them and 014/018 will use
> them — but **no screen in 017 renders one from live data**, and the guard on the
> icon registry is documented as vacuous until a status vocabulary is authored.
> Stated here so a future reader does not mistake "has a component" for "works".

## Icons — the generated manifest

```ts
// GENERATED by tools/build-icons.ts — DO NOT EDIT
export const HERO_ICONS: Record<HeroId, string>;      // 27, total, verified
export const STATUS_ICONS: Record<StatusIconKey, string>;   // 71
```

Keyed on `HeroId` from `@lmntlz/content`, so **a missing or misspelled hero icon is
a compile error** (FR-010). Regenerated by `pnpm icons:build` and diffed in CI
against a fresh build, exactly as `heroes.generated.ts` is.

## What a consumer may rely on

- Every component honours the tokens in `base.css` and contains **no colour literal**.
- Every interactive component is keyboard-reachable with a visible focus ring.
- No component fetches anything, reads `window` outside an effect, or imports
  `@lmntlz/sim/resolver` or `/ai` — the existing ESLint ban and `purity.test.ts`
  still apply.
- Every component renders at the 1280 floor without horizontal overflow.

## What a consumer must not do

- Pass a colour, a hex, or a raw `number` where `Effectiveness` is expected.
- Add a rail entry for a screen that does not exist.
- Re-implement a component privately inside `features/` — that is the debt this
  layer exists to retire.
