# Phase 0 — Research: The Design Port

**Date**: 2026-07-30 · **Spec**: [spec.md](spec.md)

Everything here was measured against the repository, not recalled. Six decisions
and one finding that changes a user story.

---

## R1 · Font delivery — `@fontsource`, self-hosted, nine faces

**Decision.** Add `@fontsource/chakra-petch`, `@fontsource/barlow` and
`@fontsource/jetbrains-mono` as client dependencies and import **only the weights
the exports use**: Chakra Petch 500/600/700, Barlow 400/500/600/700, JetBrains
Mono 400/500/700 — nine faces, `latin` subset, no italics.

**Rationale.** Constitution XIX and the Steam channel both forbid fetching from
Google at runtime: the Steam bundle loads from disk and may have no network, and a
webfont that silently fails there reflows the whole interface. `index.html` already
records that intent in a comment. `@fontsource` ships `woff2` plus `@font-face` CSS
as an npm package, so Vite fingerprints the files into `assets/` and — with
`base: './'` already set in `vite.config.ts` — emits **relative** URLs, which is
exactly what the disk-loaded build needs. All three families are OFL, so
self-hosting is licensed.

**Alternatives rejected.**
- *Google Fonts `<link>`* — a third-party runtime dependency, breaks on Steam,
  and is a privacy call nobody made.
- *Hand-downloaded `woff2` in `public/`* — no version pinning, no subsetting, and
  `public/` files skip Vite's fingerprinting, so a font update needs a cache bust
  nobody will remember.
- *Variable fonts* — smaller in theory, but only Barlow ships one of the three, so
  the pipeline would differ per family for no gain at nine faces.

**Watch for**: `font-display`. `swap` is the right default here — the fallback
stack in `base.css` is already deliberate, and a flash of fallback beats a flash of
nothing on a screen the player is mid-decision on.

## R2 · Icons — a **generated, typed manifest**, keyed off content

**Decision.** A build step reads `resources/designsystem/hero-icons/` and
`status-icons/`, copies the SVGs into the client, and emits a **generated
TypeScript manifest** whose keys are typed against `packages/content`. The same
shape as `packages/content/src/heroes.generated.ts`, and generated by a sibling of
`tools/build-content.ts`.

**Rationale.** FR-010 requires a missing icon to **fail the build**, and only a
type can do that: `tsc --noEmit` already runs before `vite build` in the client's
`build` script, so an unresolved key is a build failure rather than an empty box in
front of a player. It also satisfies Constitution XV — the mapping is derived, not
hand-authored.

**The hero mapping is total and was verified, not assumed.** A hero's `slug`
(`01-earth-bramwen`) drops its leading ordinal to give the icon name
(`earth-bramwen.svg`). Checked across the roster:

```
heroes in content : 27      mapped        : 27 / 27
hero icon files   : 28      unmapped      : none
                            icons with no hero: 00-overview-3x9
```

The single orphan is a 3×9 contact sheet, not a hero icon, and is excluded
explicitly rather than by a filter that would also swallow a real miss.

**Alternatives rejected.**
- *`import.meta.glob`* — bundles everything and resolves at runtime, so a missing
  icon is `undefined` at render. That is precisely the silent failure FR-010 exists
  to prevent.
- *SVG sprite sheet* — one request, but it defeats per-icon tree-shaking and makes
  the "does this icon exist" question a runtime `<use>` miss again.
- *`vite-plugin-svgr`* — a new dependency for JSX-ifying SVGs; the manifest needs a
  path or a raw string, not a component, and `?raw`/asset imports cover both with
  nothing added.

## R3 · ⚠️ **Status icons cannot be wired — the engine emits no statuses**

**Finding, and it changes US4.** FR-010 says *"every status effect the engine can
emit MUST resolve to an icon"*. Measured:

| | |
|---|---|
| `StatusInstance.kind` | typed `string` — **an open type, not a union** |
| Code that constructs a `StatusInstance` | **none, anywhere** |
| `apps/api/src/battle/board.ts:123` | `statuses: []` — hardcoded |
| Status icons authored | **71** |

**So FR-010 is vacuously true today.** There is no enumerable vocabulary to check a
manifest against, and an assertion over an empty set passes while proving nothing —
the exact defect this project has recorded twice (*"missing data makes the tests
GREEN"*). Wiring the 71 icons into the battle board would produce a component with
no caller, which is the other defect it has recorded five times.

**Decision — split US4 and be explicit about which half is real.**

1. **Hero icons ship wired.** 27 of 27, mapping verified, rendered by the hero card
   and the roster. Fully testable against a positive case.
2. **Status icons ship as a typed registry and a `StatusPip` component,** because
   the design needs them and 018/014 will consume them — but their **guard is
   documented as vacuous until the status system is authored**, and the test
   asserts that plainly rather than passing quietly.
3. **The anti-vacuity guard is written now**: a test that fails the moment
   `StatusInstance.kind` becomes a union or an authored status vocabulary appears,
   and does not match the icon registry. It cannot silently keep passing once there
   is something to check.

**Not in this feature**: authoring the status vocabulary. `CLAUDE.md` already lists
the 33 utility magnitudes and the reactive-power population as outstanding
*authoring*, and this is downstream of that.

## R4 · Porting method — hex to token, `style-hover` to real state

**Decision.** Port by hand, screen by screen, with a mechanical mapping table; no
automated transform.

**Rationale.** The exports carry Claude Design's runtime conventions — inline
`style=` with hex literals, a non-standard `style-hover=` attribute, an `<x-dc>`
wrapper and a `support.js` include. The translation is small and total:

| In the export | In the port |
|---|---|
| `style="…background:#1C1930…"` | the `--color-surface` token already in `base.css` |
| `style-hover="background:#241F38"` | a real `hover:` state |
| `<x-dc>` wrapper, `support.js` | dropped |
| `{{ mustache }}` placeholders | real props from real data |

An automated converter would need to understand which hex is a token and which is a
one-off, which is the judgement the port exists to apply. **A hex with no matching
token is a decision** — either a token that was missed, or a one-off that must
become one (FR-003). Automating it would inline the exception silently.

## R5 · Component API — colour is derived, and ×1.2 is unrepresentable

**Decision.** No component accepts a colour. `TypeBadge`, `RelationshipStrip` and
`HeroCard` take a `DamageType` (or a `Hero`) and derive the colour from it.

**Rationale.** Constitution XV: colour must not become a second source of truth for
a relationship. A `color` prop lets a caller paint Fire with the Water token, and
nothing would catch it.

**And the type system already enforces FR-019.** `packages/content` exports:

```ts
export type Effectiveness = 1.5 | 1.25 | 1.0 | 0.8 | 0.5;
export const BANE = 1.5, FAULT = 1.25, NEUTRAL = 1.0,
             RESISTED_SECONDARY = 0.8, RESISTED_PRIMARY = 0.5;
```

A union of literals. **A component typed on `Effectiveness` cannot be handed the
`1.2` four exports print** — it is a compile error, not a review catch. This is the
cheapest possible enforcement of the one place the port deliberately departs from
the design, and it costs nothing to adopt.

## R6 · The shell — a rail, and `THE COURT` is a group

**Decision.** Replace the four top tabs with the designed fixed-width left rail.
**`LMNTLZ Store.dc.html` (added 2026-07-30) gives the fullest version of it**, and
it is two entries longer than the Design System export showed:

```
SQUADS · ROSTER 27 · RUNE FORGE · MATCHMAKING · THE COURT · THE STORE · CODEX
                     ^^^^^^^^^^                            ^^^^^^^^^
                     both are 018 screens
```

`THE COURT` expands to Profile · Battle Record · Guild (· Chat when 014 lands).
Header carries shard balance and username. **017 builds the rail with the five
entries whose screens exist** — Squads, Roster, Matchmaking, The Court, Codex — and
`RUNE FORGE` and `THE STORE` appear when 018 builds them, which is FR-015 working
as intended rather than a shortfall. `DISPATCHES` waits on 016.

**Rationale, and this corrected an earlier misreading.** Each export marks exactly
one rail entry active with a gold icon (`#F2C744`) against grey (`#3A3357`).
Reading that state across the library:

| Export | Active entry |
|---|---|
| Roster · Codex · News | `ROSTER` · `CODEX` · `DISPATCHES` |
| **Profile · Battle Record · Guild Roster · Guild Admin** | **`THE COURT`** |

The Chat export is titled *"THE COURT · CHAT"* and Guild Creation's button reads
*"FOUND THE COURT"*. **The Court is the social half of the game and a guild is a
court**; *Court-Champion* is a rank in the same vocabulary. Nothing needs designing.

**The rail must not offer a destination that does not exist** (FR-015). This is the
inverse of the project's most repeated defect — a caller with no seam.

## R7 · Testing a visual port — where the signal actually is

**Decision.** Four kinds of test, and deliberately **no screenshot diffing**.

| Test | Catches |
|---|---|
| **Component gallery** rendered in Vitest, every component × every state | a state that was never built |
| **Token scan** — no hex literal in `src/features/` or `src/components/` outside `base.css` | the port's most likely regression |
| **Keyboard/focus** assertions per interactive component | a removed focus ring, which `base.css` forbids |
| **The existing e2e suites, unchanged** | a re-skin that broke a user journey |

**Screenshot diffing rejected.** It would be the obvious answer and it is wrong
here: the port intentionally changes every pixel of eleven screens, so every
baseline is invalid on the commit that matters, and rebaselining a diff nobody can
read is how a visual suite becomes a rubber stamp. Fidelity is checked by a human
against the export — the honest method — and the automated tests guard the things a
human reviewer *cannot* see: a missing state, an inlined hex, a lost focus ring.

**The token scan must be comment-stripped and anti-vacuity-guarded.** A scan
forbidding `#[0-9a-f]{6}` matches the comment explaining the ban, and a scan whose
glob matches nothing passes forever. Both have bitten this repo; the test asserts it
found files before asserting what is in them.
