# Icons

Generated by `pnpm icons:build` from `resources/designsystem/{hero-icons,status-icons}/`.
`icons.generated.ts` is **generated — do not edit**; CI re-runs the tool and diffs
the result, exactly as it does for `heroes.generated.ts`.

## Two registries with very different guarantees

They look symmetrical in the manifest and they are not. Knowing which is which is
the point of this file.

### `HERO_ICONS` — genuinely guarded

Typed `Record<HeroId, string>` over the **27-value literal union** generated with
the roster. An exhaustive record over a closed union means:

- a hero with no icon **does not compile**;
- a 28th hero breaks the build until its icon is added;
- `<HeroIcon heroId="h99" />` is a type error.

`tsc --noEmit` runs before `vite build`, so none of these can reach a bundle.
That is FR-010, and it is real.

### ⚠️ `STATUS_ICONS` — the guard is VACUOUS TODAY (T040)

**Nothing in the codebase produces a status.**

- `StatusInstance.kind` is an open `string`, not a union.
- No authored status vocabulary exists anywhere in `resources/`.
- `apps/api/src/battle/board.ts` hardcodes `statuses: []`.

So "every status has an icon" is **an assertion over an empty set**. It passes,
it will keep passing, and it currently proves nothing. The 71 keys are checked
against themselves — which catches a corrupted manifest and nothing else.

This is written down rather than left implicit because a green test beside a
71-entry registry reads exactly like coverage, and a future reader would have no
way to tell the difference.

#### What will make it start biting

`icons.test.ts` carries an **anti-vacuity guard** (T041) designed to fail the
moment there is something real to check. It fails when either:

1. `StatusInstance.kind` stops being an open `string` — i.e. a union appears; or
2. an authored status vocabulary shows up and does not match the 71 keys.

**Do not "fix" that test by relaxing it.** Its failure is the signal that the
registry now needs a real cross-check, and the correct response is to write one:
assert every authored status kind resolves to an icon, and every icon is claimed.

## `StatusPip` is deliberately not wired

T042 wires `HeroIcon` into `HeroCard` and the roster, and deliberately leaves
`StatusPip` unwired. There is no data for it, and a component rendered from
nothing is the defect this project has shipped repeatedly — a seam with no
caller that looks finished. It ships as a component 014/018 will call, and the
absence of a caller is recorded here rather than hidden.

## Adding or renaming an icon

1. Put the SVG in `resources/designsystem/hero-icons/` named
   `<slug-without-ordinal>.svg` — `01-earth-bramwen` → `earth-bramwen.svg`.
2. Run `pnpm icons:build`. It fails loudly on a hero with no icon and on an icon
   no hero claims, so a half-finished rename cannot pass quietly.
3. Commit both the copied asset and the regenerated manifest.

`00-overview-3x9.svg` is a contact sheet, not a hero, and is excluded **by exact
filename** — never by an ordinal pattern, which would also swallow a real miss.
